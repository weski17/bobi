# Security review – 2026-10-31

Scope: dependencies, the Bobi code (`packages`, `mcp-servers`, `scripts`, `sandbox`), the demo image and its deployment
files, and the new web-IDE access path. Method: `bun audit`, Semgrep (TypeScript and secrets rules, locally and in CI),
reading the new code, and tests against the running demo container.

## Checked and unchanged

- Semgrep on `packages`, `mcp-servers`, `scripts`, `sandbox`: 0 findings.
- Demo container: unprivileged (uid 1000), read-only root file system, all capabilities dropped, `no-new-privileges`, model
  server and Bobi server on loopback only, no route to the internet (test `tests/sandbox/demo.test.ts`).
- The demo refuses to start with a password shorter than 12 characters.
- Secrets: no keys in code, tests, logs or commits; the placeholder model key `ollama` is not a secret.
- Deployment workflow: SSH host key pinned, the registry token is valid for the job only, the password is never stored.

## Residual risks (accepted, documented in `SECURITY.md`)

- A visitor with the demo password can run commands inside the demo container (menu entry "shell"). The container
  boundary is the protection; do not mount host paths or secrets into it.
- The demo password is an environment variable of the container: host administrators can read it with `docker inspect`.
- ttyd takes the credential as a command-line argument, so a visitor with a shell in the container can read it – they
  already know it.
- Plain HTTP unless TLS is terminated in front or a certificate is mounted; the password then travels in clear text.
- A small local model is easier to steer by hostile content; the permission system (not the model) enforces limits.

## Follow-ups

- Scan the built images for known vulnerabilities (for example Trivy) in the image workflow.
- Self-hosted webview origin for the web IDE (ADR-0021) before it becomes part of the standard image.
